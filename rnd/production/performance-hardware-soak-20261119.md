# 하드웨어 가속 재측정·장시간 메모리 검사 — 2026-11-19

## 환경과 변경 범위

- Intel Iris Xe, ANGLE Direct3D11 (`Intel(R) Iris(R) Xe Graphics (0x000046A6) Direct3D11 vs_5_0 ps_5_0, D3D11`). 실제 WebGL unmasked renderer로 확인했다. SwiftShader·WARP 등 소프트웨어 렌더러는 하드웨어 실행에서 실패 처리한다.
- Headless Chrome, Windows, 720×1280/DPR 1 모바일 에뮬레이션, Vite 개발 서버. 기본 출전 유닛 2기, 오디오 비활성화. 실제 Android 검증이 아니다.
- 기존 [소프트웨어 렌더링 계측](performance-validation-20261119.md)의 적·탄환·VFX fixture를 그대로 사용한다. 순서와 관찰 시간도 동일하다.
- `tests/helpers/browser-session.mjs`: 명시적 `SMASH_BROWSER_RENDERER=hardware` 실행에서 D3D11을 사용하고 소프트웨어 래스터라이저를 차단한다. 기존 기본 실행 플래그는 유지한다.
- `scripts/gpu-probe.mjs`: 게임의 실제 WebGL 렌더러를 확인하고 JSON으로 저장한다.
- `tests/performance-browser.mjs`: 하드웨어 결과 경로 분리, 가변 관찰 시간, 선택적 15분 부하·재시작·GC 전후 메모리·리소스 계측 추가. 게임 코드·풀 크기·밸런스·새 의존성 변경 없음.

## 재현

```powershell
$env:SMASH_TEST_URL='http://127.0.0.1:5206/'
$env:SMASH_BROWSER_NO_SANDBOX='1'
$env:SMASH_BROWSER_RENDERER='hardware'
$env:SMASH_PERFORMANCE_SOAK='1'
node scripts/integration-check.mjs --serve performance-browser
```

실제 실행에서는 같은 포트에 Vite를 먼저 실행하고 `node scripts/integration-check.mjs performance-browser`를 사용했다. `node scripts/gpu-probe.mjs`로 하드웨어 가속을 먼저 확인했다. 기계 상태에 따른 편차가 있으므로 정밀한 개선 비율을 보장하지 않는다.

## 장시간 검사 방법

25초 고부하 관찰 36회(관찰 시간 합계 최소 900초)를 수행한다. 각 구간 전 1.2초 준비가 있고 구간 종료 때 전투 개체를 정리한다. 6구간마다 실제 `handlePlayerDeath`로 GameOverScene에 진입한 뒤 새 GameScene을 시작한다. 총 6회 재시작한다. 방 진행을 인간처럼 플레이하는 검사는 아니며 반복 전투 정리와 씬 생명주기에 초점을 맞춘 합성 부하 검사다.

매 구간에서 GC 전 JS 힙, 씬 자식·물리 body·collider·씬/게임 이벤트 리스너·풀·씬 수를 기록한다. 3구간마다 강제 GC 후 힙을 기록하고 재시작 직후에도 GC 후 메모리를 기록한다. 재시작 직후는 풀 준비 전이므로 준비된 전투 구간의 힙과 직접 같은 조건으로 비교하지 않는다. JS 힙·backing storage는 전체 프로세스·GPU 메모리를 의미하지 않는다.

## 장시간 결과와 검증

고부하 관찰 시간 합계 **900.573초(15분 0.573초)**, 준비·정리·GC·재시작을 포함한 장시간 구간 경과 시간 **946.474초(15분 46.474초)**. 단기 재측정을 포함한 전체 스위트는 1,093.578초였다. 36구간과 재시작 6회를 완료했다.

- 장시간 구간별 평균 FPS: 60.0002~60.0035. 프레임 p95: 16.9~17.0ms.
- 36구간 모두 준비된 전투 상태의 씬 자식 567개, 물리 body 225개, collider 3개, 씬 리스너 56개, 게임 리스너 26개를 유지했다. 적/탄환/파티클 풀은 64/160/120개, 씬 수는 10개였다.
- 재시작 직후에는 매번 씬 자식 118개, 물리 body 1개, collider 3개, 씬/게임 리스너 56/26개, 적/탄환/파티클 풀 0/0/4개로 돌아왔다. 이후 전투에서 같은 크기의 풀을 다시 준비했다.
- 마지막 정리 후 활성 적·탄환·파티클·보스 VFX·위험 영역과 계측용 씬 리스너는 모두 0이었다. 런타임 예외·VFX 실패가 없었다.

### 검증

- 성능 스위트: 22회 단기 측정 + 36회 장시간 구간 + 재시작 6회, 개체 수·예외·종료 정리·15분 관찰 시간 검사 통과. 통과 여부는 고정 FPS 기준이 아니라 계측 조건의 무결성을 검사한다.
- `npm test`: 279개 통과, 실패 0개. 로그: `artifacts/performance-hardware-20261119/unit-tests.log`.
- `npm run build`: strict TypeScript·Vite 통과. 기존 500kB 초과 번들 경고 유지. 로그: `artifacts/performance-hardware-20261119/build.log`.
- 기존 기본 플래그 경로(소프트웨어 렌더링)로도 브라우저 도우미의 게임 부팅·MenuScene 대기 완료를 확인했다.
- 신규 스크립트 구문 검사와 변경한 추적 파일의 `git diff --check` 통과.
- `code-review` 검토: 하드웨어 플래그는 선택 실행에만 적용하고 기본 경로를 유지한다. 원본 소프트웨어 결과를 덮어쓰지 않는다. 게임 코드 변경·그룹 중복 업데이트·새 의존성이 없고 계측 리스너는 `finally`에서 해제된다. 이번 변경 범위에서 추가 회귀 문제를 발견하지 않았다.

## 한계와 다음 작업

이 결과는 이 PC의 기본 편성·오디오 비활성 합성 부하 결과다. 자연스러운 방 이동·정비 거래·최대 편성·오디오 동시 실행 전체를 검증한 것은 아니다. 실제 Android와 GPU/프로세스 전체 메모리는 측정하지 않았다. 사용자의 Android 실기기 검증 생략 상태를 유지한다.

다음 메모리 조사에서는 동일 상태의 반복 재시작 전후 heap snapshot을 비교해 소폭 증가분의 보유 객체를 확인한다. 이후 최대 편성과 BGM·전투음이 함께 실행되는 조건에서 같은 계측을 적용한다. 이번 측정만으로 성급한 최적화나 풀 축소는 적용하지 않았다.
