## A. 프로젝트 종합 평가

**핵심 게임 루프와 저장·성장 모델이 연결된 고도화된 MVP다. 출시 전에는 상태 보존의 두 경계 조건과 모바일 품질 검증을 먼저 해결하는 것이 효과적이다.** 소환→조합→편성→다음 방 전투가 실제로 구현되어 있고, 자동 테스트와 debug APK 빌드까지 갖췄다. 문서만 존재하는 프로토타입 단계는 지났다.

잘 구현된 부분은 다음과 같다.

- `SquadRoster`가 거래의 원천이며 재료 중복·잔액·정원·오래된 견적을 다시 검사한다. 실패 시 상태 보존과 성공 시 단일 차감이 모델 테스트에 포함된다.
- 영웅/분대 분리, 개별 HP·부활, 22종 유닛, 고정·조건 조합과 ★ 승급, 각성·강화·유물·재능·클래스·영구 성장이 실제 연결되어 있다.
- 적과 탄환의 생명 ID, 적중 기록 초기화, 처치 보상 표식, 스테이지 진행 게이트가 풀 재사용과 중복 보상을 방어한다.
- 저장은 v1/v2 검증·이전 정상본·종료 표식·손상 데이터 보존을 갖춘다. 단순 JSON 덤프보다 방어가 충분하다.
- 가상 조이스틱/액티브의 포인터 소유권·취소·blur, 중첩된 배경/모달 정지, 외부 리스너 해제, VFX 상한과 정적 배경 캐시가 있다.

부족한 부분은 구현의 양보다 일관성과 검증 범위다. 편성 변경은 동료 전투 상태를 버리고, 일시정지는 모든 전투 타이머에 같은 의미로 적용되지 않는다. 모바일 HUD의 작은 글자/입력, 안전영역, 장시간 성능과 사람 플레이 난이도는 아직 별도 검증이 필요하다. main의 보스 전용 시청각 연출도 공통 도형·합성음 단계다.

가장 큰 기술 위험은 `GameScene`에 시간·전투·보상·저장·표시가 함께 모여 있어 기능별로 서로 다른 상태 규칙이 생기기 쉽다는 점이다. 80개 TypeScript 파일 약 9,198행 중 `GameScene`이 약 1,735행을 차지한다. 정적 import 그래프에서는 순환 참조를 발견하지 않았다. 분석은 `.ts`의 정적 import 기준이며 동적 런타임 의존성 전체의 무순환 증명은 아니다.

**출시 준비 상태:** 웹/모델 검사와 CI debug 패키지 생성은 확인했다. release 서명·스토어 배포·실기기 입력/복귀/성능·사람 플레이 난이도까지 완료했다고 판정할 근거는 없다. 이 보고서에서 P0 결함은 확정하지 않았다.

### 재현 근거와 정상 방어

01은 실제 `PlayerSquad` fixture에서 기본 사수 HP1→70, 사망 HP0/reviveAt12000→HP70/reviveAt0, 마력석30 유지로 재현했다. 이어 실제 브라우저의 `roster-deploy-unit_1` 버튼을 두 번 눌러 **HP1→70 및 사망 HP0→70/reviveAt0, 마력석30 유지**를 확인했다. UI의 `transact→onChanged→syncRoster` 경로까지 관찰했으며 런타임 예외는 없었다.

02는 실제 설치된 Phaser `time/Clock.js:358`이 매 update에서 RAF 시각을 `now`에 대입하기 때문에 발생한다. pause 중 값이 그대로 보이는 것만으로 재개 시 대기가 보존된다고 판단할 수 없다. 브라우저에서 scene.pause 후1,800ms를 기다리고 재개했을 때 now6354.2→8387.5ms로 뛰었고, 수호신의 lastSkillAt6354.2는 그대로여서 대기2,033.3ms가 소모됐다. 남은1,000ms 보호막도0이 되었다. 재개 후 관찰160ms를 포함하므로 약2초 전부가 활성 전투는 아니다. 모델에서는 활성 delta0·절대 시각 점프만으로 수호신 재시전, 화상6의 3틱·18 피해가 관찰됐다. 실제 Android background 이벤트 경로는 별도 미검증이다. 관측값은 [집중 재현 JSON](../artifacts/project-analysis-20261116/focused-browser.json)에 있다.

반면 다음은 결함으로 보고하지 않았다.

- `Enemy.spawn()`과 `Bullet.fire()`는 lifeId·디버프·피격 Set·관통/분열/추적 상태를 초기화한다.
- `handleEnemyKilled():1089`의 보상 표식과 `StageProgression.clearBoss():15`의 상태 게이트가 중복 처치를 막는다.
- `processSpawns():754`는 적 풀 고갈 시 필수 스폰을 큐에 남긴다. 문은 모든 웨이브 완료·예약 스폰0·활성 적0일 때 열린다(`GameScene.ts:1618`).
- 보스 사망/스테이지 전환은 적·탄환·장판·예약 스폰을 정리한다. 이 경로의 재진입 결함을 확정하지 않았다.
- 돌진 계획 거리와 600ms 실제 속도 계산은 대응한다. 충돌·감속·마지막 프레임에 따른 실제 경로 차이는 실측 대상이지 확정된 예고 불일치가 아니다.

### 경제·성장과 플레이 경험

소환은 확률형 뽑기가 아니라 가격과 결과가 보이는 지정 구매다. 간편 제작은 새 재료의 전체 비용으로 결과를 만들며, 보유 개체/★/소환권을 재료로 소비하지 않는 별도 편의 경로다. 이를 미구현 랜덤 소환이나 단순 Tier 진화와 혼동하면 안 된다.

기본2사수·30마력석, 기본 사수15, 보유16/출전6, 최소1출전 조건은 명확하다. 22종의 고정/조건 조합17개와 승급44개로 레시피61개, 지정 소환8종을 제공한다. 조합의 배치 재료 소비와 간편 제작·판매·강화/서비스 사이에는 지출 선택이 있다. 처치 보상은 `round(mineralValue * sqrt(rewardMult))`, 별도 방/스테이지 보상은 해당 정책을 사용한다. 이 구조의 경제 테스트·시드 보고서는 유용하지만 생존·시간·실제 DPS를 포함하지 않는 모델이다.

현재 간편 제작은 S1에서도22종의 제작 경로를 허용한다. 이는 기존 테스트가 보장하는 현행 규칙이며 버그가 아니다. 다만 수동 재료 확보/출전 재료 소비보다 저렴한 간편 제작 반복으로 선택이 수렴하는지는 실제 거래 로그로 확인할 가치가 있다. 티어 잠금·제작 할증을 임의로 도입하지 말고 사용자의 게임 규칙 승인과 사람 플레이 근거를 먼저 확보해야 한다.

새 유닛의 고유성은 전열 어그로·지원 회복·독/분열/추적·불사조 부활·수호신 보호막 등에서 확보했다. 장기 목표는 존재하지만 신규 사용자에게 조합 목표, 부족한 재료, 무료/유료 회복의 의미를 실제로 이해시키는지는 관찰이 필요하다. 첫 세 방에서 목표 레시피를 설정하고 다음 구매를 이해하는지, 클래스별 동일 조건 최소3런에서 도달 단계·플레이 시간·지출·피해/회복·실패 원인을 기록하는 것이 신규 기능 추가보다 먼저다.

### 측정한 성능 정보와 한계

- 소스 정적 분석: TypeScript80파일, 약9,198행. 정적 import 순환0. 모델 테스트 파일21개, 브라우저 스위트33개를 집계했다.

- 같은 기기의 동일 전투에서 프레임 시간 p50/p95·긴 프레임·GC/메모리·10분 이상과 씬10회 왕복을 기록한 다음 Graphics/자산/중복 표적 탐색의 우선순위를 정한다. 현재6동료·64적 상한에서는 공간분할을 바로 도입할 근거가 부족하다.
