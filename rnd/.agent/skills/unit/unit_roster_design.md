# Unit Roster & Combination Design (목표 설계 문서)

> **상태: 목표 설계안. 아래 구현 범위 외 항목은 완료 목록이 아니다.** 구현 시 변경한 부분만 [smash_roguelike_skill.md](../smash_roguelike_skill.md) §2에 반영하고, 공통 개발·검증 규칙은 [rules.md](../../rules.md)를 따른다. 같은 규칙을 이 문서에 복제하지 않는다.
> 모든 수치(비용·능력치)는 의도적으로 비워 두었으며 `src/config/gameData.ts`, `src/config/squadData.ts`에서 정한다. 이 도감과 조합표는 프로젝트용이며 원작 규칙이 아니다.

### 2026-11-04 구현 범위

- `UnitTypeDef`/`IngredientSpec`과 `unitData.ts`를 도입했다. 아래 20기와 기존 별빛 명궁·번개 대사제 2기를 보존해 총 22기를 제공한다. 기존 5기의 무기/스프라이트·레시피는 유지하며 티어 표시는 이 설계에 맞췄다.
- 고정/조건 레시피, 동일 유닛·동일 ★ 3기 승급(최대 ★3), 판매, 가능한 조합 수·필터·재료 직접 선택 UI를 구현했다. ★마다 기본 공격력/최대 체력은 50%씩 증가한다. 기존 T2 직접 소환은 호환성을 위해 남기고 T3 직접 소환은 STAGE 3부터 개방한다.
- 유닛 개별 체력·전열 우선 어그로·전투 불능, 12초 후/다음 방 진입 시 HP 50% 부활, 지원 회복, 가시 반사, 성기사/수호신 피해 분담을 구현했다. 12초 부활은 전원 전투 불능으로 진행이 영구 정체되는 것을 방지하는 규칙이다.
- 새 외형은 경장/중장/로브에 속성 팔레트·장식을 조합했다. 범위·관통·연쇄·감속은 기존 무기를 재사용한다.
- 화상 오라·암살 처치 쿨다운·드루이드 공격 보조·불사조 부활 연계·수호신 방어막은 아직 고유 효과로 구현하지 않았다. 속성 매트릭스, 확률 소환, 영구 발견 도감, 편성 시너지도 미구현이다. 아래 도감의 특징 전체를 구현했다고 해석하지 않는다.
- 레시피 도달성·순환·티어·참조·동일 우선순위 재료 충돌, 거래/한도/수동 재료 검증은 `npm test` 대상이다. 속성 매트릭스 테스트는 해당 기능 구현 시 추가한다.

## 1. 현행 문서의 부족한 점 / 추가 항목

### 1.1 캐릭터 확장 전에 필요한 핵심 공백

| 항목 | 문제 | 제안 |
| --- | --- | --- |
| 유닛 타입 데이터 계약 | 레시피 스키마는 있으나 `UnitTypeDef`(티어·속성·역할·태그)가 없음. 캐릭터가 늘면 `squadData.ts`가 비대해짐 | `src/types/game.ts`에 타입 추가 후 기존 5기를 동작 변화 없이 이관 |
| 개별 유닛 피해 | 적이 본체만 공격해 전열·지원 역할이 의미를 갖지 못함 | 개별 체력·어그로·사망/부활 설계 (역할 다양화의 선행 조건) |
| 레시피 그래프 무결성 | 순환, 도달 불가 유닛, 영구 제작 불가 유닛, 레시피 충돌 우선순위 규칙이 없음 | `npm test`에 그래프 검증 추가 (§4.4) |
| 경제 곡선 | 방당 수입·소환 비용·조합 비용·보유 한도 16기의 관계가 없음 | 방 타입별 수입표와 티어별 비용 곡선 정의 |
| 소환 방식 | 지정 소환뿐 | 지정 소환 유지 + 고티어/특수 유닛용 확률 소환(레어도) 옵션 명시 |

### 1.2 있으면 좋은 항목

- **적 다양성:** 스킬 §3.3이 단순 추적뿐. 적 타입·엘리트 특성·보스 패턴이 있어야 역할 차별화를 검증할 수 있다.
- **판매/분해:** 보유 16기가 가득 찼을 때의 재화 환급 경로.
- **도감/발견 기록:** 레시피가 늘면 필수. 영구 데이터로 런 데이터와 분리한다 (rules §6).
- **편성 시너지:** 출전 속성 구성에 따른 보너스 (§5).
- **성능 예산:** 유닛 AI의 "가장 가까운 적 탐색"은 유닛 수 × 적 수이므로, 임시 배열·Vector2 생성 없이 순회한다는 규칙을 유닛 쪽에도 적용한다 (rules §3).
- **문서 구조:** 캐릭터 목록은 스킬 문서에 넣지 않고 이 문서와 데이터 파일로 분리한다.

## 2. 설계 축

- **속성(Element) 8종:** 숲(FOREST), 바람(WIND), 불(FIRE), 서리(FROST), 번개(LIGHTNING), 대지(EARTH), 암흑(SHADOW), 빛(LIGHT)
- **역할(Role) 5종:** 전열(VANGUARD), 근접(MELEE), 원거리(RANGED), 마법(MAGIC), 지원(SUPPORT)
- **티어:** T1(소환 가능) → T2~T3(조합) → T4(최종 조합)

## 3. 캐릭터 도감 (20기)

기존 5기(숲의 사수, 바람 순찰자, 불꽃 마법사, 서리 현자, 황혼 대마법사)와 기존 레시피·무기·스프라이트는 유지한다.

### 3.4 구현 의존성

- **전열 역할**(방패병, 골렘, 수호자, 성기사, 수호신)의 효과는 개별 유닛 피해/어그로 구현에 의존한다. 그 전에는 "사거리가 짧고 본체 앞에 서는 근접 딜러"로 임시 운용한다.
- **회복/대신 피해** 효과는 본체 체력 접근 API가 필요하다.
- **부활 연계**는 개별 유닛 사망·부활 설계 이후에 구현한다.
- 효과는 기존 무기 시스템(관통·연쇄·폭발·감속)을 우선 재사용하고, 새 효과가 필요하면 타입을 먼저 추가한다.

### 3.5 도트 아트 비용 절감

`src/ui/pixelCharacters.ts`가 코드 기반이므로 캐릭터마다 새로 그리지 않고 **기본 체형 3종(경장/중장/로브) × 속성 팔레트 × 장식 레이어(모자·무기·망토)** 로 조립한다. 속성 색상 팔레트를 공통화해 색만으로 속성을 인지할 수 있게 한다. 방향은 기존 규칙대로 좌우 반전으로 표현한다.

## 4. 조합 시스템

고정 레시피만으로는 20기 × 수작업이 되므로 **고정 + 조건 + 속성 매트릭스 + 승급** 4단계로 구성한다.

### 4.1 조합 유형

| 유형 | 설명 | 예시 |
| --- | --- | --- |
| 고정 레시피 | 특정 유닛 재료 (기존 방식) | 숲의 사수 2기 → 바람 순찰자 |
| 조건 레시피 | 속성·역할·티어 조건으로 재료 지정. 같은 결과를 여러 재료로 제작 | 불 속성 T2 아무 2기 + 마력석 5개 → 불사조 군주 |
| 속성 매트릭스 | 고정/조건에 걸리지 않을 때 재료 두 유닛의 (속성, 역할)로 결과 결정. 속성 8종 → 36쌍 × 역할 | 불 + 서리 → 해당 역할의 혼합 속성 유닛 |
| 승급(★) | 동일 유닛 3기 → 같은 유닛 ★2 (능력치 상승) | 숲의 사수 ×3 → 숲의 사수 ★2 |
| 숨은 레시피 | 최초 성공 시 도감에 영구 기록. 이전에는 `???`와 힌트만 표시 | |

**제약:**
- 속성 매트릭스의 결과는 **재료 중 최고 티어 이하**로 제한해 의도치 않은 최강 유닛을 막는다.
- 결과 유닛의 티어는 재료의 최고 티어보다 낮지 않아야 한다 (승급 제외).

### 4.2 우선순위와 충돌 처리

**고정 > 조건(더 구체적인 쪽 우선) > 속성 매트릭스 > 승급**

같은 재료로 둘 이상이 매칭되면 UI에서 플레이어가 선택한다. 자동 확정하지 않는다.

### 4.3 데이터 계약 (제안)

`src/types/game.ts`에 먼저 추가한다. 기존 `{ unitTypeId, count }` 재료와 호환되도록 `kind`가 없으면 `'unit'`으로 취급한다.

```typescript
type Element = 'FOREST'|'WIND'|'FIRE'|'FROST'|'LIGHTNING'|'EARTH'|'SHADOW'|'LIGHT';
type UnitRole = 'VANGUARD'|'MELEE'|'RANGED'|'MAGIC'|'SUPPORT';

interface UnitTypeDef {
  id: string;
  name: string;
  tier: 1 | 2 | 3 | 4;
  elements: Element[];
  role: UnitRole;
  tags: string[];            // 시너지·조건 레시피용
  summonable: boolean;
  summonCost?: number;
  weaponId: string;          // 기존 DroneSpec/무기 재사용
}

type IngredientSpec =
  | { kind?: 'unit'; unitTypeId: string; count: number }
  | { kind: 'query'; element?: Element; role?: UnitRole;
      minTier?: number; maxTier?: number; count: number };

interface RecipeDef {
  id: string;
  ingredients: IngredientSpec[];
  resultUnitTypeId: string;
  resultCount: number;
  cost: number;
  priority: number;
  hidden?: boolean;
}
```

유닛 개체의 `star`(★ 단계)는 인스턴스 데이터로 두고, 유닛 개체는 기존처럼 고유 인스턴스 ID로 구분한다.

### 4.4 UI·검증 규칙

- 보유 목록에서 **"지금 가능한 조합 N개"** 를 자동 표시한다. 불가능한 조합은 부족한 재료를 표시한다.
- 조건 재료의 자동 선택 순서는 **미배치 > 낮은 ★ > 낮은 티어**이며, 플레이어가 수동 변경할 수 있다. 소모될 개체를 확정 전에 반드시 표시한다.
- 기존 원칙을 그대로 적용한다: 확정 시 재료 종류·수량·인스턴스 중복·잔액·변경 후 보유/배치 공간 재검사, 실패 시 재료와 재화 유지, 배치 중 재료 소모 시 전투 개체·예약 공격 정리.
- **레시피 그래프 테스트 (`npm test` 추가 대상):**
  - 모든 결과 유닛이 T1(소환 가능 유닛)에서 도달 가능한가
  - 결과 티어가 재료 최고 티어보다 낮지 않은가
  - 순환 의존이 없는가
  - 모든 `unitTypeId`·`weaponId`가 실존하는가
  - 같은 재료로 우선순위가 동일한 레시피가 충돌하지 않는가
  - 속성 매트릭스 결과가 티어 제약을 지키는가

## 5. 편성 시너지 (선택)

출전 6기 중 같은 속성 개수에 따라 보너스를 준다.

| 조건 | 예시 효과 |
| --- | --- |
| 같은 속성 2기 | 해당 속성 고유 효과 소폭 강화 (예: 불 → 화상 확률) |
| 같은 속성 4기 | 효과 대폭 강화 (예: 서리 → 감속 강화) |

- 출전 목록이 바뀔 때 **한 번만** 계산하고 매 프레임 재계산하지 않는다.
- 복수 속성 유닛은 각 속성에 모두 집계할지 주 속성만 집계할지 구현 전에 확정한다.
